## 1. Library 7: Asterisk.Sdk.Activities

### 1.1 What Activities Does

The Activities library provides a programmatic IVR engine. Instead of writing Asterisk
dialplan (extensions.conf with `Background()` + `WaitExten()` + digit extensions), you
define call flows in C# as a chain of activities:

```
Answer → PlayPrompt → GetDigits → Branch(digit) → Transfer/Queue/Hangup
```

Each activity is a discrete unit of work. The engine executes them sequentially on a
per-call basis, maintaining state across the workflow. Think of it as a state machine
where transitions are driven by caller input (DTMF) and application logic rather than
dialplan priority lines.

Activities run inside an AGI or ARI session. The SDK connects to Asterisk, takes
control of the channel, and drives the call through the activity graph.

### 1.2 Current State

PbxAdmin does not use Activities. The existing IVR demo (extension 200, Spanish menus)
is built with traditional Asterisk dialplan generated by `DialplanGenerator`. The load
test IVR scenario (`IvrNavigationScenario`) calls extension 200 but does not send
DTMF — it only validates that Background/Playback apps appear in CEL.

### 1.3 Infrastructure Requirements

**Activity Engine Host:** A background service within the load test app that:
- Connects to Asterisk via AGI (FastAGI on port 4573) or ARI (port 8088)
- Registers activity workflows for specific extensions (e.g., 300-309)
- Processes incoming calls through the activity graph
- Reports workflow completion/failure events

Answer → PlayPrompt("main") → GetDigits(1) → Branch:

    PlayPrompt("sales-sub") → GetDigits(1) → Branch:

## 2. Library 8: Asterisk.Sdk.Audio

### 2.1 What Audio Does

The Audio library provides a codec and audio processing pipeline:

- **Resampling:** Convert between sample rates (8000 Hz, 16000 Hz, 48000 Hz). Asterisk
  internally uses 8kHz for narrowband and 16kHz for wideband codecs. External
  integrations (WebRTC, AI services) often need 16kHz or 48kHz.
- **Codec Conversion:** Transcode between PCM formats — G.711 ulaw (North America),
  G.711 alaw (Europe/international), signed linear 16-bit (slin16, used by
  AudioSocket and AI pipelines).
- **Audio Mixing:** Combine multiple audio streams (conference bridges, monitoring).
- **Silence Detection:** Identify pauses in speech — used for VAD (Voice Activity
  Detection) in AI pipelines and recording trimming.

plays pre-recorded scenarios but the load test never captures or analyzes the audio.

### 2.4 What to Test

#### 2.4.1 Resampling Accuracy

**Test flow:**
1. Generate a 1kHz sine wave at 16000 Hz (source)
2. Use `Asterisk.Sdk.Audio` to resample to 8000 Hz (ulaw native rate)
3. Resample back to 16000 Hz
4. Compare original and round-tripped audio using cross-correlation

**Validation:** The round-trip resampling should preserve the fundamental frequency.
Cross-correlation coefficient between original and round-tripped signal must be > 0.95.
Amplitude difference must be within +/-1 dB.

This test runs in-process (no Asterisk needed) — it validates the SDK's resampling
algorithms directly.

#### 2.4.2 Codec Conversion Round-Trip

**Test flow:**
1. Start with PCM slin16 audio (known test tone)
2. Encode to ulaw (G.711 mu-law)
3. Decode back to slin16
4. Encode to alaw (G.711 A-law)
5. Decode back to slin16
6. Encode ulaw, transcode to alaw, decode — full cross-codec path

**Validation:** G.711 is lossy (8-bit companded from 16-bit linear). Expected SNR for
a single encode/decode cycle is approximately 38 dB for a 1kHz test tone. After
round-trip (encode → decode → encode → decode), SNR should remain above 30 dB.

This is also an in-process test of the SDK codec functions.

#### 2.4.3 End-to-End Audio Through Asterisk

**Test flow:**
1. SipAgent A calls SipAgent B through Asterisk (direct extension dial)
2. Agent A sends the 1kHz test tone via RTP
3. Agent B captures incoming RTP frames into a buffer
4. After 5 seconds, both hang up
5. Compare sent audio (Agent A's source) with received audio (Agent B's buffer)

**Validation:**
- Signal-to-Noise Ratio (SNR) of received vs sent must be > 20 dB
- No RTP packet loss (received frame count within 5% of expected: 250 frames for 5s at
  20ms pacing)
- Frequency analysis: 1kHz peak present in received audio FFT
- Jitter: inter-frame arrival time standard deviation < 5ms

#### 2.4.4 Audio Mixing (Conference)

**Test flow:**
1. Three SipAgents (A, B, C) join a conference bridge via `ConfBridge()`
2. Agent A sends a 440 Hz tone, Agent B sends 880 Hz, Agent C captures
3. After 3 seconds, analyze Agent C's captured audio

**Validation:**
- FFT of captured audio must show peaks at both 440 Hz and 880 Hz
- Both frequencies present with amplitude within 6 dB of each other (Asterisk mix
  should be roughly equal)
- No frequencies above 3500 Hz (low-pass filtered by G.711 8kHz codec)

#### 2.4.5 Silence Detection

**Test flow:**
1. Create an audio buffer with pattern: 2s speech, 1s silence, 2s speech, 1s silence
2. Run SDK silence detection on the buffer
3. Validate detected silence regions

**Validation:**
- Silence detector identifies 2 silence regions
- Region boundaries accurate within +/-100ms
- Speech regions not falsely flagged as silence
- Works correctly at both 8kHz and 16kHz sample rates

#### 2.4.6 Processing Under Load

**Test flow:**
1. Spawn 50 concurrent SipAgent pairs (100 agents total)
2. Each pair: Agent A sends test tone, Agent B captures
3. All 50 calls run simultaneously for 10 seconds
4. Validate audio quality on all 50 captured streams

**Validation:**
- All 50 captures have SNR > 15 dB (slightly relaxed from single-call threshold)
- RTP packet loss < 10% across all streams
- No audio buffer overflows or underruns in SDK processing pipeline
- Total memory growth < 100 MB for 50 concurrent streams

## 3. Library 9: Asterisk.Sdk.VoiceAi + VoiceAi.AudioSocket

### 3.1 What VoiceAi and AudioSocket Do

**AudioSocket** is an Asterisk protocol (introduced in Asterisk 16) that streams raw
audio bidirectionally over a TCP connection. When a call hits the `AudioSocket()`
dialplan application, Asterisk opens a TCP connection to an external server and streams
16-bit signed linear audio at 8000 Hz (slin16) in both directions. The external
application can process the audio (speech recognition, AI, recording) and send audio
back (TTS playback, IVR prompts).

The protocol is simple:
- **Frame type 0x00:** UUID (16 bytes, sent once at connection start)
- **Frame type 0x01:** Silence indicator
- **Frame type 0x10:** Audio data (slin16, 8000 Hz, 20ms frames = 320 bytes)
- **Frame type 0xFF:** Hangup/error notification

**VoiceAi** builds on AudioSocket to provide a higher-level pipeline:
- Receives audio frames from AudioSocket
- Feeds them to an STT (Speech-to-Text) provider
- Returns transcription results
- Accepts text input, runs it through a TTS (Text-to-Speech) provider
- Sends synthesized audio back through AudioSocket to the caller

In production, VoiceAi connects to cloud AI services (Google STT, Azure Cognitive,
OpenAI Whisper, etc.) or local models. For testing, we use mock services that return
deterministic results.

Not used anywhere. No AudioSocket configuration in the demo Docker stack. No AI

### 3.3 Infrastructure Requirements

#### 3.3.1 AudioSocket TCP Server

A TCP listener embedded in the load test app that implements the Asterisk AudioSocket
protocol:

```csharp
public sealed class AudioSocketServer : IAsyncDisposable
{
    private readonly int _port;                    // Default: 9092
    private TcpListener? _listener;
    private readonly ConcurrentDictionary<Guid, AudioSocketSession> _sessions = new();

    /// <summary>Starts listening for AudioSocket connections from Asterisk.</summary>
    public Task StartAsync(CancellationToken ct);

    /// <summary>Gets a session by its Asterisk-assigned UUID.</summary>
    public AudioSocketSession? GetSession(Guid uuid);

    /// <summary>Gets all active sessions.</summary>
    public IReadOnlyCollection<AudioSocketSession> ActiveSessions { get; }

    /// <summary>Event fired when a new AudioSocket connection arrives.</summary>
    public event Action<AudioSocketSession>? SessionStarted;

    /// <summary>Event fired when a session ends (hangup or disconnect).</summary>
    public event Action<AudioSocketSession>? SessionEnded;
}

public sealed class AudioSocketSession : IAsyncDisposable
{
    public Guid Uuid { get; }
    public DateTime StartedAt { get; }
    public int FramesReceived { get; }
    public int FramesSent { get; }
    public bool IsActive { get; }

    /// <summary>Captured audio buffer (all received frames concatenated).</summary>
    public ReadOnlyMemory<byte> CapturedAudio { get; }

    /// <summary>Sends an audio frame back to Asterisk (slin16, 320 bytes).</summary>
    public ValueTask SendAudioFrameAsync(ReadOnlyMemory<byte> frame, CancellationToken ct);

    /// <summary>Sends a complete audio buffer, paced at 20ms per frame.</summary>
    public Task SendAudioAsync(ReadOnlyMemory<byte> pcmAudio, CancellationToken ct);
}
```

### 3.4 What to Test

### 3.6 AudioSocket Protocol Implementation Details

The AudioSocket wire protocol is straightforward. Each message has a 3-byte header:

```
Byte 0:    Frame type (0x00=UUID, 0x01=Silence, 0x10=Audio, 0xFF=Error)
Bytes 1-2: Payload length (16-bit big-endian)
Bytes 3+:  Payload data
```

For UUID frames, the payload is 16 bytes (UUID in binary).
For audio frames, the payload is 320 bytes (160 samples * 2 bytes per sample, slin16).
For error frames, the payload is a null-terminated error string.

The server must:
1. Accept TCP connection
2. Read frames in a loop
3. Parse frame type and length
4. Buffer audio data
5. Optionally send audio frames back (same format: type 0x10 + length + data)
6. Handle disconnect (TCP close or error frame)
